## 摘要
站点可靠性工程（SRE）智能体的基准通常是情景式的：注入一个故障，智能体接收一个事件任务，然后对其响应进行评分。但生产运行并非如此。事件通过带有噪声的告警浮现，在时间上相互重叠，且往往源于代码或配置变更。我们提出 SRE-Marathon，一个面向长时程、连续 SRE 运行的基准。智能体以固定节奏被调用，获得累积的告警历史和持久化工作区，同时操作一个真实运行的双区 Kubernetes 部署；故障编排器则按照带随机种子、经生产校准的调度注入相互重叠的故障。精选的代码与配置变更通过同一构建流水线部署，该流水线也可用于修复。每次运行都被记录到密封数据包中并离线评分：Marathon-Score 对每个注入故障在关联、定位和修复上的有序进展给予计分，所有指标均基于记录的系统证据确定性计算。在三个应用、每次运行约六十个故障的设置下，10 种方法中表现最佳者仅达到 100 分中的 41.3 分。智能体往往能够关联并定位故障，但几乎无法在故障仍然活跃时完成修复。

## Abstract
Benchmarks for site reliability engineering (SRE) agents are typically episodic: one fault is injected, the agent receives an incident task, and its response is scored. Production operation is not. Incidents surface through noisy alerts, overlap in time, and often originate from code or configuration changes. We present SRE-Marathon, a benchmark for long-horizon, continuous SRE operation. An agent is invoked at a fixed cadence with cumulative alert history and a persistent workspace while operating a live two-zone Kubernetes deployment as a fault orchestrator injects overlapping faults according to a seeded, production-calibrated schedule. Curated code and configuration changes deployed through the same build pipeline available for repair. Each run is recorded into a sealed bundle and scored offline: Marathon-Score credits each injected fault for ordered progress through correlation, localization, and repair, with all metrics computed deterministically from recorded system evidence. Across three applications and about sixty faults per run, the best of 10 methods reaches only 41.3 out of 100. Agents often correlate and localize faults, but almost never complete repairs while the faults remain active.

# SRE-Marathon 论文总结

## 1. 核心问题与整体含义

- **研究动机**：现有 SRE 智能体基准普遍采用“情景式（episodic）”协议——从干净环境开始、注入单个故障、给智能体明确的事件任务、提交答案即结束。这与真实生产运维严重不符。
- **生产运维的三大特征**：
  - 问题通过**带噪声的告警流**浮现，而非显式事件描述；智能体需自行判断是否存在事件、哪些症状属于同一事件。
  - 大量事件源于**系统内部变更**：大型云服务中代码与配置缺陷合计占高严重事件的 39.5%，因此回滚、重配置、fix-forward 是核心修复手段。
  - **事件相互重叠**，干预有代价与副作用，评估不能只看诊断准确率，还要看是否及时、安全、高效地解决。
- **现有基准的不足**：多依赖 chaos 原语、单事件独立评估，忽略重叠、累积错误、连带影响与运维成本；在 SREGym 上前沿智能体已达 72.6% 诊断成功、78.5% 缓解成功，但这种强结果建立在被大幅简化的生产模型上。
- **整体含义**：论文提出 SRE-Marathon，将 SRE 评估从“孤立事件解决”推进到“持续生产运行”，揭示当前智能体在持续负载下**几乎无法完成修复**这一核心瓶颈。

## 2. 方法论

### 2.1 核心思想

- 让智能体在**真实运行的微服务系统**上持续值守：按固定节奏被调用，接收累积告警历史与持久工作区，面对按种子化、生产校准调度连续注入且相互重叠的故障。
- 故障既可来自外部 chaos，也可来自**通过正常构建流水线部署的代码/配置变更**，迫使智能体考虑回滚、重配置与 fix-forward。
- 每次运行记录为**密封数据包（sealed bundle）**，所有指标离线、确定性地从系统证据计算，避免模型裁判。

### 2.2 系统组成

- **Live system**：三个微服务应用在持续负载下运行——20 服务 OpenTelemetry Demo Astronomy Shop、11 服务 Online Boutique、41 服务 Train Ticket；Astronomy Shop 额外采用双区 Kubernetes 部署与故障转移。
- **Fault Orchestrator**：种子化调度，决定故障类型、位置、开始与回退时间；同一发布与种子保证故障序列一致。
- **故障目录**：700 个故障，覆盖三类机制：
  - **代码缺陷（224）**：人工编写的补丁引入缺陷，通过 lint 与单元测试，模拟逃逸 CI 的缺陷。
  - **配置缺陷（203）**：通过部署清单变更引入错误设置。
  - **Chaos 测试（273）**：部署错误、依赖故障、基础设施、数据库/网络、认证故障等直接注入。
- **Marathon 调度**：按 Ghosh et al. (2022) 的生产分布采样类别（代码缺陷 27.0%、依赖 16.4%、基础设施 15.8%、部署 13.2%、配置 12.5%、数据库/网络 10.5%、认证 4.6%）；故障强度在运行期内增长四倍，单个故障活跃 4–12 分钟后被回退。
- **智能体接口**：19 个 MCP 工具，分读、报告、动作、受保护动作四类；固定间隔 Δ=120s 调用，单次预算 110s；工作区跨调用持久；变更操作经过策略执行层，检查目标、限制范围、记录禁止操作。

### 2.3 评估指标与公式

- **三阶段生命周期**：
  - **关联（Correlation）**：告警与事件正确匹配，`Corr = (1/|F|)Σ af`。
  - **定位（Localization）**：精确识别故障服务与责任制品，`Loc = (1/|F|)Σ bf`。
  - **修复（Repair）**：在故障仍活跃时执行干预并经系统证据验证恢复，`Rep = (1/|F|)Σ cf`。
- **Marathon-Score**：
  - `100 · (1 − d/2) · (1/|F|) Σ_f (af + af·bf + af·bf·cf) / 3`
  - 其中 `d=1` 表示存在尝试的禁止操作；三项有序加权，只有先关联才能定位、先定位才能修复；完整处理得满分。
- **其他指标**：
  - **干预风险 Risk**：`(nout + nforb)/(nexec + nforb)`，衡量越界动作与禁止操作。
  - **服务退化 Degrad. Level**：`Dagent / Dno-action`，对错误率与慢请求比例按流量加权积分。
  - **MTTD/MTTL/MTTR**：检测、定位、修复的中位时间。
  - **成本**：模型调用次数、token 消耗、估计美元成本。

## 6. 主要结论与发现

- **端到端修复是主要瓶颈**：最佳方法 Keep-agent 仅得 41.3/100，Runbook 33.5，其余 Kimi K2.5 方法 3.7–25.6，GPT-5.6 Luna 方法 8.2–31.3。
- **修复率极低**：所有方法的 `Rep` 最高仅 0.024；只有 Keep-agent 有端到端处理（Online Boutique 上 1/57 与 2/59）。多数得分来自关联与定位。
- **检测较快但用户影响差异大**：Kimi K2.5 上高关联方法检测时间 146–189s（约 1–2 次调用）；退化水平因骨干而异，有的恶化到 124.3%–150.5%，有的改善到 77.4%–93.5%。
- **负载增加时“报告多、行动少”**：ReAct 报告调用从 3.9 增至 35.5 次/调用，读取仅 8.9→13.8；动作始终不超过 5.3 次/调用。
- **关联稳定、定位分化、修复罕见**：随故障累积，关联保持相对稳定；定位区分方法；修复始终最弱，Kimi K2.5 上任何时刻均不超过 6%。
- **并发是修复失败的主要来源**：同一 ReAct 在 5 故障短运行得 38.9、10 故障 34.8、marathon 仅 25.4；端到端处理比例从 16.7%→6.7%→0.0%，而关联变化很小。
- **行动常落在正确服务但无效**：多数执行动作命中活跃故障的服务，却未能修复；ORBIT 几乎不行动，OpsMem 仅执行 5 次动作。
- **成本与效果无对应**：RAG 与 Keep-agent 仅用 569k/685k token，而工具密集智能体用 5.4M–7.2M token，但性能并无一致优势。
- **案例揭示行动选择低效**：Claude Code 能识别正确服务，却先尝试两次无效配置变更和一次被策略层拒绝的清单补丁，最终回滚过晚，错过修复窗口。

## 7. 优点

- **贴近生产的连续长时程设计**：重叠故障、噪声告警、强度递增、变更驱动故障通过真实构建流水线部署，显著区别于单故障情景式基准。
- **真实系统验证干预效果**：在 live 微服务系统上评估恢复、用户退化与连带影响，而非仅检查最终答案。
- **确定性离线评分**：密封运行记录 + 无模型裁判，所有指标可复现、可重算，适合作为强化学习的可验证目标。
- **多维指标与有序计分**：Marathon-Score 强制关联→定位→修复的顺序，并纳入安全风险、服务退化、时延与成本。
- **工程完备性**：700 故障目录、生产校准分布、种子化调度、双区 K8s、19 个工具、策略执行层与禁止操作记录。
- **广泛且公平的对比**：10 种方法、2
