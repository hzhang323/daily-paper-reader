## 摘要
近年来，大语言模型（LLMs）的快速发展重塑了软件工程，使自主代码智能体能够通过规划、执行并迭代利用外部工具来解决复杂任务。除了实现功能正确性之外，这些智能体还必须在整个开发生命周期中忠实遵循过程指令和约束。然而，现有基准通常关注最终功能正确性，或将指令遵循评估局限于单轮、通用聊天或简单代码生成场景，导致多轮智能体编程中的指令遵循问题尚未得到充分探索。为弥补这一空白，我们提出 MTAC-IFBench，一个针对这一关键能力的综合基准。它包含多轮渐进式软件开发指令，其约束多样，涵盖 6 个一级类别和 18 个二级类别。每个实例平均包含 7.04 轮和 91.33 个约束，对当前 LLMs 构成了严峻挑战。为使评估可靠，我们为每个约束和功能需求构建检查清单，并集成验证脚本和评判智能体来验证每个检查项。MTAC-IFBench 揭示了现有代码智能体在多轮指令遵循方面存在显著缺陷，其性能随着交互会话变长而迅速下降。

## Abstract
Recently, the rapid development of large language models (LLMs) has reshaped software engineering by enabling autonomous code agents that plan, execute, and utilize external tools iteratively to tackle complex tasks. Beyond achieving functional correctness, these agents must faithfully follow process instructions and constraints throughout the development lifecycle. However, existing benchmarks typically focus on final functional correctness or confine instruction-following evaluation to single-turn, general chat or simple code generation scenarios, leaving instruction-following in multi-turn agentic coding underexplored. To bridge this gap, we propose MTAC-IFBench, a comprehensive benchmark for this critical capability. It features multi-turn progressive software development instructions with diverse constraints spanning 6 primary and 18 secondary categories. With an average of 7.04 turns and 91.33 constraints per instance, it poses a rigorous challenge to current LLMs. To make the evaluation reliable, we construct a checklist for each constraint and functional requirement, and integrate verification scripts and judge agents to verify each checklist item. MTAC-IFBench identifies significant deficiencies in existing code agents in multi-turn instruction-following, with their performance degrading rapidly as the interaction session grows longer.

## 1. 核心问题与研究动机

- **背景**：大语言模型驱动的代码智能体（如 Claude Code、Kilo）已能自主规划、执行并调用外部工具，从"人写代码"转向"智能体自主开发"。此类智能体不仅需生成功能正确的代码，还须在整个开发生命周期中严格遵守过程指令与约束，这是其可靠落地生产环境的前提。
- **两大挑战**：
  - 约束高度异构：不仅涉及生成内容与代码，还涵盖环境交互与智能体工作流。
  - 交互本质是多轮的：用户会迭代新增或修改需求，要求智能体在多轮间持续保持约束一致性而不发生上下文退化。
- **现有基准的空白**：
  - 智能体编程基准（SWE-Bench、Terminal-Bench 等）聚焦最终功能正确性，忽视过程指令与约束遵循。
  - 指令遵循基准（ComplexBench、CodeIF 等）局限于通用对话或单文件代码生成。
  - 少数拓展至智能体场景的工作（AgentIF、OctoBench 等）仍局限于单轮交互、约束类型有限、缺乏系统化约束分类。
- **整体含义**：MTAC-IFBench 是首个面向**多轮智能体编程**的指令遵循综合基准，填补了"过程约束遵循"评测的空白。

## 2. 方法论

### 2.1 核心思想
构建带有多轮渐进式软件开发指令、且蕴含丰富过程约束的实例，并通过"检查清单 + 混合验证"方式实现可靠评测。

### 2.2 约束分类体系（Taxonomy）
- 提出 **6 个一级类别 + 18 个二级类别** 的层级化分类：
  - **Content**：Keyword（关键词）、Persona（人设语气）、Format（格式模板）
  - **Language**：Response Language、Comment Language、File Encoding
  - **Quantity**：Range、Exact Value、Complexity（目录层级/嵌套深度/圈复杂度等）
  - **Style**：Layout、Naming、Paradigm
  - **Environment**：File Path、File Operation、Logging
  - **Workflow**：Tool Usage、Orchestration、Testing

### 2.3 数据集构建流程（半自动化流水线）
1. **指令收集与多轮扩展**：
   - 从人工专家与现有基准（ZfrontendBench、CCBench）收集单轮软件开发指令。
   - 用 Gemini-3.1-Pro 将单轮指令扩展为 5–10 轮的渐进式多轮序列（首轮搭骨架，后续逐轮新增/修改功能）；每条做两次独立扩展，得 **374 个多轮序列**。
2. **分类体系引导的约束集成**：
   - 逐轮迭代的"集成—验证"流程，由 Seed-2.0-Pro 执行。
   - 先将约束集成到仓库策略文件（如 Claude.md，全程不可变），再逐轮注入用户指令。
   - 采样策略：按类别曝光次数的平方反比赋权，优先欠曝类别以保证分布均衡。
   - 允许新增约束或**替换**先前约束（每轮新增/修改上限 2 条），模拟真实需求的动态演化。
   - 每轮校验清晰性、一致性、完整性、可行性，失败重试最多 5 次，仍失败则丢弃整个序列。
3. **检查清单生成与评估方法设计**：
   - 生成每轮的**约束检查清单**与终局的**功能检查清单**。
   - 每项按特性分配评估方式：确定性项用**验证脚本**（代码评估），主观/复杂项用**裁判智能体**（Judge Agent）。
4. **人工质量检查**：
   - 17 名大学生对指令的清晰性、一致性、完整性、可行性做逐条审查，缺陷指令剔除，并修正检查清单，确保与需求一一对齐。

### 2.4 评估指标（文字说明）
- 设第 t 轮约束清单为 C_t，z_{t,j}∈{0,1} 表示第 j 条约束是否满足；F 为功能清单，y_k∈{0,1}。
- **CSR_t**：第 t 轮满足约束的比例（软性通过率）。
- **C-ISR_t**：第 t 轮所有约束均满足的严格指示值（全部满足才为 1）。
- **BSR**：最终项目可执行性；**FSR**：功能满足比例；**F-ISR**：所有功能均满足的严格指示值。
- 实例级分数在数据集上取平均。

### 2.5 评估协议
- 将多轮指令依次输入代码智能体，逐轮生成交互轨迹与代码项目。
- **代码评估**：由 Claude-Opus-4.6 生成 Python 验证脚本，将项目路径与末轮响应作为输入，输出二值判断。
- **裁判智能体**：基于 Claude Code 框架，功能清单用 Claude-Sonnet-4.6，约束清单用 DeepSeek-V4-Pro；采用 IF-Critic 的一次性评估全部约束策略；允许使用 Playwright 模拟浏览器交互、截图验证，前端项目用 npm 自动部署并提供 HTTP URL。

## 6. 主要结论与发现

1. **基准极具挑战性**：即使领先模型 GLM-5.2 也有约 **20% 的约束未遵循**；CSR 在 60.6%–80.4%，但 C-ISR 大多 **低于 10%**，说明"完美遵循全部过程约束"极难。
2. **性能随交互轮次快速衰减**：所有模型的 CSR 与 C-ISR 随轮次增加持续下降，多数模型在 **6 轮后 C-ISR 降为 0**；更强的模型多轮鲁棒性更好，衰减更慢。
3. **过程约束比功能需求更难**：所有模型的 C-ISR 显著低于 F-ISR，说明以最终结果为导向的评测会掩盖开发过程中的关键失败。
4. **类别差异明显**：在 Encoding、File Path 等孤立静态约束上接近满分，但在 **Orchestration、Paradigm、Naming、Quantity** 等需要全局状态维护与精确量化控制的约束上表现很差。
5. **来源差异明显**：仓库策略文件中的约束比用户指令中的约束具有更强的长程鲁棒性；用户指令中**更新已有约束比新增约束更难**，反映智能体难以跟踪演化的用户意图。
6. **框架影响显著**：模型在 Claude Code 下普遍优于 OpenCode（如 GLM-5.2 CSR 从 80.4% 降至 76.8%，C-ISR 从 12.7% 降至 6.7%），但 OpenCode 下的多轮衰减更平缓；模型层级大体稳定，中低段模型的细粒度排名受框架影响较大，强调需明确报告 harness。
7. **约束放置**：放在仓库策略文件中效果最好，系统提示与用户提示效果相近。

## 7. 优点

- **问题定位精准**：首次系统性地将指令遵循评测拓展到"多轮智能体编程"这一真实且关键场景。
- **分类体系完备**：6 大类 18 小类的层级化约束分类，为约束合成与覆盖分析提供系统化框架。
- **数据构建严谨**：半自动化流水线 + 类别均衡采样 + 逐轮校验重试 + 17 人人工质检，质量可控；引入仓库策略文件与约束动态更新机制，贴近真实开发。
- **评估方法可靠且灵活**：脚本验证与裁判智能体混合，兼顾确定性与复杂语义验证；采用 IF-Critic 一次性评估策略提升效率；前端任务引入 Playwright/npm 进行真实用户行为验证。
- **可靠性有据**：与人工标注一致率超过 92%（约束）/85.5%（功能），功能项一致率甚至超过两位标注者之间的一致率。
- **分析深入**：从轮次、类别、来源、放置位置、框架等多个角度剖析失败模式，结论具有实践指导意义（如"重要约束应写入仓库策略文件"）。

## 8. 不足与局限

- **评估偏差风险**：采用模型作为裁判，可能存在自我增强偏差与冗长偏差，影响特定模型的评估正确性；虽有一致性验证，但未引入多裁判辩论等去偏机制。
- **裁判智能体成本高**：需多轮工具调用与环境交互，成本显著；论文承认这是必要权衡，未做系统性的成本优化。
- **场景覆盖有限**：虽涵盖多种开发任务，但真实场景还包括安全漏洞修复、数据库 schema 迁移等，尚未覆盖。
- **数据规模偏小**：100 个实例、9,133 条约束，相对于 SWE-Bench（2,294 例）等规模较小，可能限制统计稳健性与结论泛化性。
- **单轮约束密度不均衡**：每轮仅新增/修改至多 2 条约束，但约束在整个会话中累积生效，导致后期轮次约束负担远高于早期轮次，可能对轮次衰减分析产生混淆。
- **算力与训练细节缺失**：未报告 GPU 资源，无法评估可复现的计算成本；主要依赖闭源模型 API，复现受 API 可用性限制。
- **应用限制**：基准主要针对仓库级代码智能体，结论未必适用于非代码类智能体任务；且裁判模型（Claude/DeepSeek）的选择本身可能引入平台相关的偏差。
