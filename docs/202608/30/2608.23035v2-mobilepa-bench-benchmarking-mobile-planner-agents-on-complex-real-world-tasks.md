## 摘要
随着端侧LLM代理演进为个人副驾驶，移动操作系统已成为这一范式的关键试验场，使得严格的能力评估至关重要。然而现有基准分为两大阵营，各自存在关键盲点：以GUI为中心的基准测试表面层面的屏幕操作，却忽略了后台工具使用和长程规划；而静态函数调用基准则依赖于离线API匹配，与真实运行时约束脱节。为弥合这一差距，我们提出了\textbf{MobilePA-Bench}——一个交互式、有状态、以工具为中心的基准，用于评估移动规划代理的工具调用与规划能力。MobilePA-Bench运行在可执行沙箱上，该沙箱维护实时应用数据库并返回结构化反馈，覆盖13个功能领域和212个逼真的移动工具。除基本工具使用外，它还从三个高级维度评估核心规划代理：\emph{(1)~子代理协作}——将复杂任务分解并委派给有能力的子代理进行专门处理；\emph{(2)~记忆使用}——回忆存储的记忆、用户档案和过往偏好以解决隐式请求；以及\emph{(3)~技能使用}——调用预封装的复合技能，而非从头规划每一步。大量实验表明，当前前沿LLM在移动场景中仍不可靠：在严格工具排序、权限限制和意外运行时错误下，性能急剧下降。通过将交互式函数调用沙箱与基于证据的验证相结合，MobilePA-Bench既可作为实用的诊断基准，也可作为智能体强化学习的交互基础——加速可靠移动代理的开发。

## Abstract
As on-device LLM agents evolve into personal copilots, the mobile operating system has become a key testbed for this paradigm, making rigorous capability evaluation essential. Yet existing benchmarks fall into two camps, each with a critical blind spot: GUI-centric benchmarks test surface-level screen manipulation while overlooking background tool use and long-horizon planning, whereas static function-calling benchmarks rely on offline API matching that is detached from real runtime constraints. To close this gap, we present \textbf{MobilePA-Bench}, an interactive, stateful, and tool-centric benchmark for evaluating the tool-calling and planning abilities of mobile planning agents. MobilePA-Bench runs on an executable sandbox that maintains live application databases and returns structured feedback, spanning $13$ functional domains and $212$ realistic mobile tools. Beyond basic tool use, it evaluates a central planning agent along three advanced dimensions: \emph{(1)~Sub-agent Collaboration}---decomposing a complex task and delegating specialized work to capable sub-agents; \emph{(2)~Memory Usage}---recalling stored memories, user profiles, and past preferences to resolve implicit requests; and \emph{(3)~Skill Usage}---invoking pre-packaged composite skills instead of planning every step from scratch. Extensive experiments show that current frontier LLMs remain unreliable in mobile settings: performance drops sharply under strict tool ordering, permission limits, and unexpected runtime errors. By pairing an interactive function-calling sandbox with evidence-based verification, MobilePA-Bench serves as both a practical diagnostic benchmark and an interactive foundation for agentic reinforcement learning---accelerating the development of dependable mobile agents.

## 1. 论文的核心问题与整体含义

**研究动机**：随着端侧 LLM 代理逐渐演变为个人移动副驾驶，评估其真实能力变得至关重要。然而现有移动智能体基准存在两大盲区：
- **GUI 中心基准**（如 AndroidWorld、OSWorld）只关注屏幕点按与视觉布局解析，忽视了后台工具使用、长程规划和系统级 API 编排；

**核心问题**：真实移动任务（如多日旅行规划）需要同时具备记忆检索、复合技能调用、多模态输入处理和 GUI 子代理委派等异构能力，但缺乏一个统一、有状态、能反映真实运行时约束的评估平台。

**意义**：论文提出 MobilePA-Bench，作为面向移动规划代理（Mobile Planner Agent）的诊断性与强化学习可用并重的基准，弥补上述两类基准之间的空白。

## 6. 主要结论与发现

- **整体性能上限低**：最强模型 Claude-Opus-5 整体加权得分仅 75.52%，13 个模型中 7 个低于 70%，远未达到可靠自主部署水平。
- **子代理协作与记忆使用是主要瓶颈**：子代理得分 43.82%–77.53%，记忆得分最低仅 33.78%–64.63%，说明个性化上下文的应用远难于直接工具执行。
- **无普遍占优的规划器**：Claude-Opus-5 领跑工具与技能（83.85% / 78.00%），Gemini-3.1-Pro 领跑子代理（77.53%），Qwen-3.8-Max 领跑记忆（64.63%），但没有任何模型四维同时领先。
- **技能复用能缓解长程误差**：技能使用普遍高于记忆使用，说明预封装多步流程可降低从头规划的误差累积。
- **错误跨能力级联**：真实任务往往横跨多个维度，单维度的错误率叠加导致端到端成功率大幅下降。
- **规划器缺乏校准的克制力与自适应恢复**：面对权限错误、歧义约束时，模型倾向过早产生幻觉式工具调用，而非追问澄清或根据反馈调整策略。
- **通用结论**：当前前沿 LLM 不足以支撑全自动移动操作系统，需结合状态化反馈的强化学习、严格的智能体间通信与记忆-工具对齐训练。

## 7. 优点

- **统一的多维评估框架**：在同一个有状态环境中同时评估工具调用、子代理协作、记忆和技能四个维度，避免了各维度孤立评测与现实脱节的问题。
- **状态化、可交互的沙箱**：真实数据库后端 + 动态反馈，使评估具备高保真度；同时去耦视觉渲染开销，支持高吞吐、确定性回放，RL 友好。
- **证据对齐的三桶验证**：根据任务内在语义选择 Tool Call / State Change / Agent Behavior 验证方式，避免了一刀切评分带来的误判。
- **环境摩擦内置**：权限拦截、参数缺失、依赖顺序等现实障碍被系统地注入测试，能暴露模型在真实运行时错误下的恢复能力。
- **开源与全面复现**：完整开源 1,705 个任务、评估数据集和沙箱环境，便于后续智能体训练诊断与强化学习研究。
- **详实的场景分布**：提供了 13 个高层场景、89 个二级子类的层次化分布分析（1,530 查询快照）。

## 8. 不足与局限

- **子代理任务量偏小**：仅 89 个任务，样本量不足以支撑统计可靠的结论；且只评估了委派质量，未验证下游子代理实际执行效果，无法衡量端到端闭环质量。
- **候选工具召回参数的敏感性未知**：固定 \( N=15 \)，未消融不同召回数量对结果的影响；若正确工具不在候选集中，模型将必然失败。
- **记忆维度覆盖有限**：376 个记忆任务仅用 search_user_memory 一种工具，未涉及写入、替换、删除等更丰富的记忆操作（虽在数据分布图中标出，但未报告子类型分项）。
- **基准去耦了视觉感知**：虽然有意将视觉解析从中心规划中解耦，但这也意味着无法评估规划器在真实手机 GUI 环境中的综合表现，需要额外的端到端验证。
- **纯英文/合成数据偏差**：任务由模板和规则合成，可能与真实用户语言表达存在分布差异，存在一定的数据偏差风险。
- **业界模型版本假设**：论文中出现 Claude-Opus-5、Qwen-3.8-Max 等未来版本号，实际开源社区无法验真，可复现性受限。
- **未报告计算开销与标注成本**：缺乏对沙箱吞吐量、推理成本、任务构建人力的定量描述，难以评估实际应用门槛。
