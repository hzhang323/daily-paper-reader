## 摘要
AI 智能体通常以是否完成任务来评估。在交互式服务场景中，即使智能体成功完成任务，也可能因反复提问、执行冗余搜索或进行本可避免的修改而令用户感到沮丧。我们提出 RideWay——一个面向有状态工具调用环境中网约车智能体的以效率为中心的基准，以及 Efficiency Utility——一种成功门控指标，它相对于任务特定的参考工作量，对成功轨迹中的超额工具调用和面向用户的轮次进行折减。人类配对偏好校准相对惩罚权重，反映了一种总体服务流程权衡：额外对话往往会造成明显的摩擦，而额外工具使用有时可以验证约束条件或保持用户意图。在 58 个任务和 24 个模型上，拟合得到的超额轮次惩罚约为超额工具调用惩罚的两倍。在任务不相交的留出偏好上，Efficiency Utility 的总体准确率为 78.7%：当轨迹在轮次上不同时达到 90.6%，但当轨迹仅在工具调用上不同时仅为随机水平——这也是人类标注者一致性最低的维度。因此，RideWay 使交互效率能够与任务成功一同被衡量，同时揭示了基于计数的工具使用评估的边界。

## Abstract
AI agents are usually evaluated by whether they complete a task. In interactive service settings, a successful agent can still frustrate users by asking repeated questions, performing redundant searches, or making avoidable revisions. We introduce RideWay, an efficiency-centered benchmark for ridehailing agents in a stateful tool-calling environment, together with Efficiency Utility, a success-gated metric that discounts successful trajectories for excess tool calls and user-facing turns relative to task-specific reference effort. Human paired preferences calibrate the relative penalties, reflecting an aggregate service-workflow trade-off: extra dialogue often creates visible friction, whereas extra tool use can sometimes verify constraints or preserve user intent. Across 58 tasks and 24 models, the fitted penalty for excess turns is about twice that for excess tool calls. On task-disjoint held-out preferences, Efficiency Utility achieves 78.7% accuracy overall: 90.6% when trajectories differ in turns, but chance-level accuracy when they differ solely in tool calls - the axis on which human annotators agree least. RideWay therefore makes interaction efficiency measurable alongside task success, while exposing the boundary of count-based tool-use evaluation.

# RideWay 论文详细总结

## 1. 核心问题与整体含义

- **研究动机**：现有工具使用型语言智能体（tool-using language agents）的评测几乎只关注"是否完成任务"这一结果指标。但在打车、客服等交互式服务场景中，一个成功完成任务的智能体仍可能因反复提问、冗余搜索、无谓修改而显著增加用户负担。
- **关键矛盾**：
  - 成功轨迹之间在交互效率上差异巨大，但成功率评估把它们一视同仁。
  - 额外的工具调用不一定是浪费：可能是验证约束、保留用户偏好所必需；而额外的用户对话轮次往往直接带来可见摩擦。因此不能简单用统一的动作计数来惩罚。
- **核心问题**：如何衡量成功智能体的**交互效率**，而不仅仅是它是否成功？
- **整体含义**：论文提出 RideWay 基准与 Efficiency Utility 指标，把"效率"作为与"成功"正交的第二层测量维度，使交互效率可与任务成功率并列评估，同时划定了"基于计数的工具使用评估"的能力边界。

## 2. 方法论

### 2.1 核心思想
- 继承 Success weighted by Path Length（SPL）的骨架：成功门控 + 任务相对参考基线 + 仅惩罚超出基线的努力。
- 两处关键改造：
  1. 将单一"路径长度"拆为**两个可观测轴**——面向用户的对话轮次（turns）与后端工具调用（tool calls）。
  2. 两轴相对代价不预先设定，而是从**人类配对偏好**中学习校准。

### 2.2 关键定义与公式
- 记任务为 $x$，轨迹为 $\tau$，$c_{tool}(\tau)$、$c_{turn}(\tau)$ 为观测到的工具调用数与助手对话轮次。
- 每个任务由人工标注者充当客服智能体交互，取中位数得到任务特定参考下限 $f_{tool}(x)$、$f_{turn}(x)$。
- 超额量：
  - $e_{tool}(\tau) = \max\{0, c_{tool}(\tau) - f_{tool}(x)\}$
  - $e_{turn}(\tau) = \max\{0, c_{turn}(\tau) - f_{turn}(x)\}$
- **Efficiency Utility**：
  $$U(\tau) = \text{success}(\tau)\,\lambda_{tool}^{\,e_{tool}(\tau)}\,\lambda_{turn}^{\,e_{turn}(\tau)}$$
  - 失败轨迹得 0；恰好处于参考下限的成功轨迹得 1；每多一次工具调用或一轮对话，按乘法折减。
  - 采用指数形式的理由：Bradley–Terry 模型需要可加性代价，$\exp(-\cdot)$ 是唯一能将可加代价转为逐单位乘法折减的单调映射。

### 2.3 偏好校准流程
- **构造配对**：仅在**已通过成功门控的同一任务成功轨迹池**内构造配对，排除"是否成功"和"任务难度"两个混淆因素。
- 采样覆盖 tool-only、turn-only、mixed 三类权衡对，中文熟练标注者看到完整对话与任务背景，但不知模型身份、计数与指标分数，允许平局。
- **Bradley–Terry 拟合**：
  - 线性超额代价 $C(\tau) = a\,e_{tool}(\tau) + b\,e_{turn}(\tau)$，$a,b \ge 0$。
  - $p_{ij} = \sigma(C(\tau_j) - C(\tau_i))$，用带 L2 正则（$\gamma=0.3$）的二元交叉熵拟合。
  - 转换回指标：$\lambda_{tool} = e^{-a}$，$\lambda_{turn} = e^{-b}$，因此 $U(\tau) = \exp(-C(\tau))$。

## 3. 实验设计

### 3.1 基准与场景
- **RideWay**：中文网约车（ridehailing）有状态工具调用环境。
- **工具集**：26 个工具（18 个读工具 + 8 个写工具），覆盖地址查找、POI 搜索、地理编码、订单查询、估价、司机匹配、航班信息、路径搜索、下单/取消/改目的地等。
- **任务划分**：
  - **rh44**（44 个任务）：用于校准。
  - **custom14**（14 个任务）：任务不相交的留出验证集，长时程、角色驱动、含闲聊干扰。
  - 共 58 个任务，覆盖起点-终点定位、订单类型选择、显式/推断偏好、上下文延续、时间推理、历史回忆、歧义位置、司机推荐、弱信号推断、路线规划、中途修改等能力标签。
- **成功门控**：三评委 LLM 面板（hy3-preview、seed2.0-lite、grok4.3），每位评委跑 3 次取多数，至少 2/3 评委通过才算成功；三个评委均不在 24 个被评模型池中，以限制自偏好偏差。
- **用户模拟器**：GPT-4.1（固定）。

### 3.2 对比方法与诊断基线
- **Tool-only**：只用工具轴。
- **Turn-only**：只用轮次轴。
- **Equal-cost length**：$e_{tool} + e_{turn}$。
- **Turn-first / Tool-first 字典序**：某一轴绝对优先。
- **Log/sqrt 单调变换**：验证函数形式影响。

### 3.3 评测规模
- 24 个非思考型 LLM 配置，分 4 个能力层级（A 前沿闭源 / B 强闭源与开源 / C 中等 / D 较小），每个任务 3 次尝试。
- 原始轨迹：rh44 得 3,168 条，custom14 得 1,008 条。
- 配对标注：320 条校准投票（rh44）+ 80 条留出投票（custom14）。
- 列表式验证：10 个任务、80 条轨迹放入 4 个效率桶。
- IAA 研究：23 对纯工具轴 + 17 对轮次/混合轴；评委面板人工审计 75 条轨迹。

## 6. 主要结论与发现

- **拟合惩罚不对称**：$a = 0.1235$（工具），$b = 0.2448$（轮次），即 $\lambda_{tool}=0.8838$、$\lambda_{turn}=0.7829$；一次超额用户轮次的对数惩罚约为一次超额工具调用的 **2.01 倍**（90% bootstrap 区间 [1.40, 2.96]）。
- **留出偏好预测**：整体准确率 **78.7%**，Kendall $\tau_b = 0.573$。
  - 轮次不同时准确率 **90.6%**；但仅当轮次差 ≤3 时仅 58.3%，差 >3 时为 100%（头部数字主要由大差距对贡献）。
  - 纯工具对准确率 **50.0%**，人类投票恰好 11:11 平分。
- **列表式验证**：10 个任务上 Kendall $\tau_b$ 全为正，均值 0.488、中位数 0.553；优于 tool-only 与 turn-only。
- **成功率与效率的关系**：整体 Spearman $\rho = 0.785$，但在最高的 12 个模型上关系变平（$\rho = -0.161$）。典型例子 **mimo** 成功率最高（87.4%）但效率仅排第 10。
- **惩罚确实在起作用**：496 条成功轨迹中仅 28.8% 零超额工具调用、34.3% 零超额轮次、10.3% 两者皆零。
- **边界结论**：工具轴在总体上信息量存在，但**不能作为逐次调用的浪费标签**——原始计数无法区分"必要验证/偏好保留"与"无谓消耗"。
- **评委面板可靠性**：与人工盲审一致率 90.7%（Cohen's $\kappa = 0.813$）；Tier A/B 完美一致（30/30），7 处分歧全部来自 Tier C/D。

## 7. 优点

- **问题定位准确**：把"效率"作为与"成功"正交的评测层，明确区分面向用户的对话摩擦与后端工具工作，避免将二者混为一谈。
- **指标设计有理论依据**：指数形式并非随意选择，而是由 Bradley–Terry 可加代价经 $\exp(-\cdot)$ 映射自然导出，并与成功门控自然复合。
- **惩罚权重由人类偏好学习而非手工设定**：避免了"逐次调用即浪费"的武断假设，且非负约束在最优解处松弛，说明工具惩罚由数据支撑。
- **实验严谨性高**：任务不相交留出验证、多种诊断基线、分层分析、bootstrap 区间、参考下限扰动鲁棒性、L2 敏感性扫描、无约束拟合检验。
- **对评测工具本身做审计**：不仅评估智能体，还用人工盲审检验 LLM 评委面板的可靠性，并报告 IAA，透明度高。
- **诚实地划出边界**：明确承认工具轴接近随机、头部准确率由大差距对带动、单领域中文设定不可直接外推，避免过度宣称。
- **可复现性完善**：代码、数据、复现脚本公开，附 HOW_TO_REPRODUCE.md、DATA_CARD.md，并说明哪些数字需要非默认调用。

## 8. 不足与局限

- **领域与语言单一**：仅中文网约车场景，校准权重可能反映本地服务规范；英文工具标识可能偏向英文 API grounding 更强的智能体；跨语言/跨领域外推需另行验证。
- **测量维度受限**：Efficiency Utility 只统计可观测的轮次与工具调用，排除隐藏推理、延迟、货币成本、语气、用户满意度与安全性；原始计数无法区分必要工作与浪费。
- **留出集规模有限**：80 条留出偏好、22 条纯工具对有向对，超额轮次样本稀疏，统计功效有限。
- **标注覆盖不足**：多数配对只有一位主标注者；IAA 是针对性检查而非全面重标；列表式与评委审计均为部分覆盖。
- **依赖自动化组件**：用户模拟器（GPT-4.1）与三评委 LLM 面板均为自动组件，人工审计只覆盖 75 条随机轨迹，不能替代真实用户或状态验证。
- **模型池限制**：刻意排除 thinking 模型；不报告 token 成本相关性（因 tokenizer、冗长度、服务差异导致不可比）。
- **纯工具轴接近随机**：工具调用计数的语义盲区是方法的固有边界，论文自身也承认这是"基于计数的工具使用评估"的局限。
- **潜在误用风险**：效率指标可能产生"尽量减少交互"的压力，即便澄清本可更好服务用户；论文强调它必须与安全、正确性、用户控制与满意度评估互补，且不得用于真实网约车运营决策。
