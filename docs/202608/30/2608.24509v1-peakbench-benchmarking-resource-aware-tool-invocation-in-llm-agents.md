## 摘要
LLM智能体日益通过调用多个工具来解决问题，其中并行执行对于低延迟至关重要，但难以安全地管理。现有的智能体基准主要评估工具选择、参数生成以及大多在串行执行下的端到端成功，在很大程度上忽视了有效的并行化和资源受限的调度。这一缺失的调度维度造成了一种实际故障模式：串行执行安全但缓慢，而资源无关的并行执行快速但易发生可避免的资源溢出。为解决这一差距，我们引入了PeakBench，一个可执行的多工具工作流基准，具有基于执行的依赖注解和测量的资源配置文件。评估此类工作流的一个核心挑战是归因问题：失败和低效率可能源于错误的依赖规划、糟糕的资源受限调度，或两者兼有。PeakBench通过一个两部分评估框架应对这一挑战，该框架将逻辑规划与物理调度分开，并为每个维度提供专用指标。使用此框架，我们表明强大的逻辑规划并不能可靠地转化为在资源约束下安全或高效的执行。我们进一步表明，暴露资源信息可以减少可避免的溢出并提高资源利用率，使PeakBench成为诊断资源感知智能体行为的有用试验平台。代码可在https://github.com/Czzzk/Staggering-the-Peaks获取。

## Abstract
LLM agents increasingly solve tasks by invoking multiple tools, where parallel execution is essential for low latency but difficult to manage safely. Existing agent benchmarks primarily evaluate tool selection, argument generation, and end-to-end success under mostly serial execution, largely overlooking valid parallelization and resource-constrained scheduling. This missing scheduling dimension creates a practical failure mode: serial execution is safe but slow, while resource-agnostic parallel execution is fast but prone to avoidable resource overflows. To address this gap, we introduce PeakBench, a benchmark of executable multi-tool workflows with execution-grounded dependency annotations and measured resource profiles. A central challenge in evaluating such workflows is attribution: failures and inefficiencies may arise from incorrect dependency planning, poor resource-constrained scheduling, or both. PeakBench addresses this challenge with a two-part evaluation framework that disentangles logical planning from physical scheduling, with dedicated metrics for each dimension. Using this framework, we show that strong logical planning does not reliably translate into safe or efficient execution under resource constraints. We further show that exposing resource information can reduce avoidable overflows and improve resource utilization, making PeakBench a useful testbed for diagnosing resource-aware agent behavior. Code is available at https://github.com/Czzzk/Staggering-the-Peaks.

- **归因难题**：端到端任务失败无法区分是由于（1）错误识别了工具间的依赖/并行关系（逻辑规划失败），还是（2）在依赖关系正确的前提下，物理调度未能满足资源容量约束（调度失败）。现有单一日志得分无法拆解这两类错误。

## 2. 方法论

### 2.1 整体框架：把智能体工作流视为约束调度问题

作者将多工具执行形式化为一个受约束的系统调度问题（公式1）：

- 目标：最小化调度延迟（Scheduling Latency, SL）
- 约束1（逻辑成功）：Φ(x; V, S)=1——工具选择、参数、依赖结构必须足以完成任务。

关键设计在于将这两个约束拆分为两个独立的评估维度（公式2），从而解决归因问题。

### 2.3 两维评估协议（图3）

**维度一：逻辑规划（Dependency Analyzer）**

- 输入：用户查询、工具及服务器描述
- 输出：预测的依赖/并行结构（表示为DAG）
- 指标：
  - **GED（Graph Edit Distance）**：预测图与真实图之间的最小编辑距离
  - **Edge F1**：预测先决条件边的精确率与召回率（惩罚幻觉依赖与漏缺依赖）

**维度二：物理调度（System Scheduler）**

- 输入：执行验证过的真实结构（oracle输入，排除规划不确定性）+ 资源画像 + 机器容量
- 输出：每个工具调用的启始时间戳（调度延迟）

- 指标（公式7-8）：
  - **SL（Scheduling Latency）**：端到端完成时间
  - **CVA（Capacity Violation Area）**：归一化的容量溢出面积——最核心的安全指标，为0表示完全未超限
  - **strict MRU（严格平均资源利用率）**：仅在CVA=0时奖励高利用率

### 2.4 RASC（Resource-Aware Scheduling Context）

- 一个轻量基线方法：在调度输入中显式暴露资源元数据（每个工具调用的预计执行时长、资源占用、机器容量），不加额外训练或优化器。
- 核心对比逻辑（公式9）：
  - 无画像的基线调度器 π_base = π_θ(q, R⋆)：只看到逻辑结构，容易“资源盲”，全部尽早就绪启动
  - RASC调度器 π_RASC = π_θ(q, R⋆, P, C)：看到资源画像和容量，可进行有意识的错峰调度

## 6. 主要结论与发现

1. **强逻辑规划≠强资源感知调度**：GPT-5和DeepSeek-V4-Pro在依赖提取上表现最强，但其无画像调度成绩与较弱规划者并无显著差距——模型级散点（图4）显示模型不聚集在匹配对角线上，案例级相关系数也很弱（表7）。
2. **无画像模型并非简单ASAP**：它们会通过添加保守延迟来降低CVA并改善strict MRU，但代价是显著更高的调度延迟——说明模型在缺乏资源信息时只能靠“盲目谨慎”来避免风险。
3. **RASC将粗粒度的保守延迟转化为目标化错峰**：对大多数模型，RASC在降低延迟的同时降低CVA并提升strict MRU——资源画像帮助模型用精确的错峰替代一刀切的等待。
4. **RASC接近最优规则调度器**：在CVA上几乎追平Best Rule（2.938 vs. 2.925），且strict MRU更高（0.165 vs. 0.141），但收益具有**模型依赖性**——DeepSeek-V4-Flash在RASC下CVA反而略增（+0.034），说明仅暴露资源信息不一定确保模型能将其转化为有效的时序安排。
5. **RASC增益的来源**：主要发生在small和medium容量配置下（资源冲突更频繁）；消融（表9）表明单提供时长信息无增益，核心增益来自CPU和内存画像（可行率从74.9%提升至87.6%），这是可操作的诊断结论。
6. **归因框架有效**：通过两维解耦，能明确识别出“规划强而调度弱”的模型类型，这是传统端到端基准无法做到的。

## 7. 优点与亮点

1. **问题定义新颖且重要**：将“峰值负载”形式化为LLM智能体评估中的独立维度，填补了资源约束调度评估的空白。
2. **两维解耦设计巧妙**：用“固定一个维度、单独评估另一个维度”的方式彻底解决失败归因难题，是方法论上的清晰贡献。
3. **执行验证取代纯人工标注**：通过沙箱中扰动执行顺序来恢复依赖关系，使得基准结构有真实运行依据而非仅靠LLM/人工推断，且94%的人工审计一致性验证了可行性。
4. **资源画像的多维性与冷/热启动区分**：5维资源足迹覆盖完整硬件栈，静态/动态分量区分持久占用与瞬时突增，贴近真实系统的资源行为。
5. **RASC作为诊断工具有实用价值**：不需要重训模型或引入外部优化器，仅通过上下文工程即可获得显著的溢出减少和利用率提升，为后续研究提供了简单可复制的基线。
6. **丰富的辅助实验**：噪声鲁棒性、输入消融、容量敏感性等实验使结论更具稳健性和可解释性。

2. **模型与数据时效性存疑**：论文中的模型（GPT-5、GLM-5、DeepSeek-V4、Kimi-K2.5、Claude Sonnet 4.6）和部分参考文献的年份为2026年，arXiv时间为2026年8月，可能存在虚拟/未来模型命名问题；如果这些模型是真实的，其API配置细节未提供（温度、采样参数、重试策略等），影响实验的客观复现性。
3. **工作流规模有限**：300个工作流（150/100/50分层），硬场景仅50个，且调用数上限为15次——对于真实大规模agentic工作流（可能涉及几十上百次工具调用）的泛化性存疑。
4. **资源画像数据来自三个LLM生成输入的平均**：这种方法可能无法覆盖真实用户请求的资源分布长尾，且画像的准确度没有通过更广泛的指令分布验证。
5. **模拟真实性的局限**：调度仿真采用固定的容量配置，未考虑排队延迟、带宽竞争、局部性效应等系统性非线性现象；真实系统行为可能比仿真更复杂。
6. **未涉及端到端联合评估**：虽然解耦设计有利于归因，但现实中模型需要同时完成两维任务，论文没有报告端到端联合场景下（模型自己完成规划和调度）的综合成绩及其与Separate维度的对比关系。
7. **某些模型在RASC下无增益甚至负增益**（如DeepSeek-V4-Flash在CVA上反而增加），论文对背后的原因分析相对简略，没有深入检验模型是否误解了资源画像或产生了错误的延迟策略。
8. **非LLM基线选型有限**：仅使用了ASAP、串行和列表启发式方法，未与更现代的强化学习调度器或整数规划求解器对比，也未评测这些经典方法在不同工作流规模下的扩展性。
