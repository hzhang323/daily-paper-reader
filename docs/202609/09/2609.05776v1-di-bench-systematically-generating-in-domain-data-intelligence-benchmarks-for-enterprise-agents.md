## 摘要
评估企业智能体在领域特定基准测试上的表现至关重要，然而公开的基准测试很少评估智能体是否能够将业务知识与分析计算相结合，并且手动构建此类基准测试成本高昂。我们提出了DI-Bench，一个用于生成数据智能（DI）现实基准测试的流水线，数据智能是从大量企业数据中提取洞察的实践。为了模拟需要计算和知识检索的现实DI任务，DI-Bench在数据表、维度、指标和文档之间构建工件链接图，以形成涉及结构化数据和相关知识的问询。基准真实答案通过查询执行获得，随后进行LLM问询生成和验证。应用于两个公开数据集后，该流水线生成了一个包含731个任务的基准测试，覆盖知识检索、分析计算和规则依据推理。为了展示该基准测试的区分性和难度，我们评估了四个模型，揭示了一个重要发现：在执行检索到的业务规则修改计算的的计算任务时，模型的准确率仅为32%。

## Abstract
Evaluating enterprise agents on domain-specific benchmarks is critical, yet public benchmarks rarely evaluate whether agents can integrate business knowledge with analytical computation, and constructing such benchmarks manually is costly. We present DI-Bench, a pipeline for generating realistic benchmarks for data intelligence (DI), the practice of extracting insights from large volumes of enterprise data. To emulate realistic DI tasks that require both computation and knowledge retrieval, DI-Bench builds an artifact linkage graph over data tables, dimensions, metrics, and documents to form questions involving structured data and associated knowledge. Ground truth answers are derived via query execution, followed by LLM question generation and validation. Applied to two public datasets, the pipeline produces a 731-task benchmark covering knowledge retrieval, analytical computation, and rule-grounded reasoning. To show the discriminatory capability and difficulty of the benchmark, we evaluate four models, revealing a substantial finding: models achieve only 32% accuracy when doing computational tasks where retrieved business rules modify the computation.

## 论文核心问题与整体含义

### 研究动机与背景
- **核心问题**：企业 LLM 智能体在数据智能（DI）任务上（如回答业务问题）需要同时具备知识检索、SQL 查询和业务规则应用能力，但现有基准未能覆盖这一完整链路。
- **现有基准的不足**：Text-to-SQL 基准（如 Spider、BIRD）将所需知识内联在问题中；Spider 2.0 的文档为单任务定制且直接指定；数据分析基准（如 InfiAgent-DABench）无文档语料；文档型问答基准（如 FinanceBench）只将文档作为数值来源，而非计算规则来源。
- **构建成本高**：人工构建此类基准每任务约需 35 分钟，737 任务约需 420 小时；纯 LLM 生成的答案缺乏确定性保证。

## 方法论

### 核心思想
DI-Bench 提出一个**端到端可迁移的流水线**，通过「先算答案再出题」的反向生成范式，将数据库、指标目录和业务规则文档组织起来，**通过程序化查询执行获得确定性的 gold answer**。

### 关键组件与流程

#### 1. 工件链接图（Artifact Linkage Graph, ALG）
- **节点**：表、指标、规则文档、维度（共 71–76 个节点）。
- **边**：6 种依赖关系，核心是 `rule → metric` 边，表示规则文档**因果性地改变**指标的计算结果（而非仅表面语义相关）。
- **构建方式**：结构化部分的边从 schema 和指标定义直接提取；规则相关边由 LLM 从自然语言文档中识别；通过**反事实检查**过滤虚假关联。

#### 2. 子图采样（Subgraph Sampling）
- 从每个指标节点出发沿边扩展，枚举/采样合法连通子图作为任务骨架。
- 用 MMR（Maximal Marginal Relevance）在质量与多样性间平衡选择候选子图。
- 覆盖性增强：保证每个指标和规则文档至少出现一次；对低于目标数量的分析类型进行补充采样。

#### 3. 真实答案的计算（Ground Truth Computation）
- **SQL 实例化**：用数据中的具体值替换模板中的维度筛选占位符；将每个规则的效应编码为结构化 SQL 修改（如追加 WHERE/HAVING 子句），与基础 SQL 组合后执行。
- **分析类型增强**：根据 9 种分析类型（点查询、趋势、比较、排名、显著性检验、阈值穿越、反事实、分解、知识检索），对 SQL 结果进行后处理形成结构化答案。

#### 4. 反向问题生成（Backward Question Generation）
- LLM 根据已知的 gold answer、指标名和分析类型生成自然语言问题，问题不暴露数据库内部细节，不暗示应检索哪个规则文档。

#### 5. 自动化验证（Automated Validation）
- **程序化过滤**：正则检查结构缺陷、内部标识符泄露、答案完整性等。
- **LLM 质量评分**：DeepSeek V3.2 作为评判者，对 8 个二值维度（客观性、泄露、自然度、相关性、格式一致性、SQL 正确性、逻辑推理、范围一致性）打分，全部通过才准入；仅措辞类失败自动改写重评。

## 实验设计

### 数据集与 Benchmark
- **巴西电商（Olist）**：9 表、约 10 万订单、覆盖 27 个州 → 449 任务。
- **捷克零售银行（PKDD'99）**：8 表、整数日期、跨多表需更多连接 → 282 任务。
- **知识库构造**：每领域 29 条指标定义 + 17 份规则文档（均为 LLM 生成、基于 schema 的拟造文书，非真实企业文档）。
- **最终基准**：731 个任务，按难度分三档：Knowledge（知识检索，N=137）、Knowledge + Analytics（检索并计算指标，N=419）、Knowledge + Analytics + Rule Modification（额外检索并应用修改计算的规则，N=175）；任务经两级验证，Stage 1 拒绝 21% 候选、Stage 2 拒绝余下 26%。

### 对比模型
- **Claude Opus 4.6**（最佳整体准确率 57.9%，平均 5.5 轮 LLM 调用/任务）
- **DeepSeek V3.2**（50.9%，平均 11.5 轮/任务，工具调用效率最低）
- **Claude Haiku 4.5**（49.0%）
- **Qwen3-80B**（47.9%）
- 通过 Bedrock Converse API、原生工具调用、最多 20 轮/任务、温度 0、最大输出 token 4096；评分采用带容差规则的精确匹配。

### 附加实验
- **消融（规则配对策略）**：在 175 个规则任务上比较 Graph vs Semantic vs Random 配对规则：判别有效性 82% / 29% / 22%。
- **人类专家对比**：15 个采样任务上两位 BI 专家正确率 87%，高于模型（Opus 73%、Haiku 67%、Qwen 60%、DeepSeek 53%）。
- **生成器与评判者敏感性**：Qwen 与 DeepSeek 生成问题质量相似（79.9% vs 79.6%）；4 个验证器精确率 94–96%、召回率 79–93%。
- **消除/干预分析**：规则 oracle 仅提升 0.2 个百分点（32.5%→32.7%），而去掉规则要求则提升 20.4 个百分点（32.5%→52.9%），证明瓶颈在规则应用而非规则检索。

## 主要结论与发现
- **「知识到计算」的鸿沟**：在不需计算的纯知识任务上，模型平均准确率达 82%；加入计算后退至 50%；再加规则修改则骤降至 **32%**。所有模型结果一致，说明知识增强计算是主流盲区，并非检索或工具调用本身的问题。
- **绝大多数任务的难易度与匹配要求相关**：二值判断与方向类任务（如阈值穿越、趋势）表现相对较好；排名、点查询这类要求逐行精确匹配的任务，四模型均低于或等于 35%。
- **规则检索已不是企业智能体的主要瓶颈**，如何让检索得到的业务规则在计算中得到严格且正确的地基（grounding）才是根本症结。
- 失败案例进一步印证：Claude Opus 4.6 虽能检索到规则，却在 SQL 中错误地单边加一自然日宽限；没有完成抑制后的并列排名逻辑；在反事实任务上无法同步运行双规则场景。

## 优点
- **可验证的数据生成范式**：把“LLM 直接生成问题+答案”替换成“SQL 先算出确定性答案，再给 LLM 造句”，从根本上避免了幻觉型 gold。
- **工件链接图**用形式化的 `rule → metric` 边使“文档是否影响答案”成为可检查的因果关系，避免语义相似却无关的文档误配——实验证实图选择比随机选规则高约 3 倍判别性。
- **两级自动验证**（程序化 + LLM judgment）与人审对标：通过评判者筛选出的子集在人的复核下达到 99% 通过率，显著度高。
- **完整流程已沉淀为参考实现**（附图），支持用户在自己的数据与规则文档上复制使用，工程化和迁移成本低。多类型任务覆盖度高，适合细分技能的定向评测。

## 不足与局限
- **领域泛化风险**：仅两个行业、且业务文档为合成材料（非真实企业级文档），无法充分还原生产中的歧义性、过时文档、跨团队依赖等问题。
- **资源信息缺失**：未披露模型运行所需 GPU/训练/推理时长等指标。
- **样本不均衡**：反事实、分解等复杂任务的案例数过少（N≈10–20），做类型间显著性比较时的效能不足。
- **评估口径过于刚性**：精确匹配既不给部分分，也可能对“语义等价但表达不同”的正确答案误判。
- **共享模型偏差与 LLM 验证中立性**：主生成器和评判者同为 DeepSeek 系列，易引入同源偏差；作者用 4 个 judge 和人审缓解了这一问题，并在 Appendix E 报告了相关敏感性，但共用模型的偏差不能完全消除。
- **LLM 生成的文档与真实企业的规则集之间仍有差距**，真实环境中的“规则漂移”（规则随时间变化）未被建模为多版本演化过程——虽然论文声称其流水线支持更新，但并未给出具体实现或实验验证。
