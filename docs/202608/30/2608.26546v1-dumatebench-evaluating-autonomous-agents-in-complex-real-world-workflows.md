## 摘要
自主智能体越来越多地被应用于现实环境中完成复杂的多工具工作流。然而，现有基准测试通常按应用或能力分离任务，并在比实际场景更干净、更稳定的环境中评估智能体。我们介绍了DuMateBench，这是一个从大规模生产级智能体平台收集的经过匿名化和隐私筛选的用户会话重建的真实会话基准。每个任务都保留了相关的解决前交互历史、持久化配置和工作区状态，并通过人工验证进行确认。由此产生的基准包含200个任务，涵盖8个广泛场景和17个细粒度能力类别，大多数任务需要多种能力的协同配合。我们在注入三种现实环境复杂性（不足、不稳定和噪声）的隔离Docker容器中执行这些任务，并使用混合确定性与LLM作为评判者的评估协议来评估性能。对五个具有代表性的自主智能体框架与四个最先进的LLM进行的实验揭示了在严格任务完成方面存在显著差距。补充的鲁棒性、效率和诊断分析进一步表明，环境扰动下的性能由LLM的能力和周围智能体框架共同塑造。代码和数据可在 https://dumatebench.com/ 公开获取。

## Abstract
Autonomous agents are increasingly adopted to complete complex, multi-tool workflows in real-world settings. However, existing benchmarks typically separate tasks by application or capability and evaluate agents in environments that are cleaner and more stable than those encountered in practice. We introduce DuMateBench, a real-session benchmark reconstructed from anonymized and privacy-screened user sessions collected from a large-scale production agent platform. Each task preserves the relevant pre-solution interaction history, persistent configurations, and workspace state, and is then validated through human verification. The resulting benchmark comprises 200 tasks spanning 8 broad scenarios and 17 fine-grained capability categories, with most tasks requiring multiple capability coordination. We execute these tasks in isolated Docker containers injected with three forms of real-world environmental complexity: Insufficient, Unstable, and Noisy, and assess performance using a hybrid deterministic and LLM-as-Judge evaluation protocol. Experiments across five representative autonomous-agent frameworks paired with four state-of-the-art LLMs reveal substantial gaps in strict task completion. Complementary robustness, efficiency, and diagnostic analyses further show that performance under environmental perturbations is jointly shaped by the capabilities of the LLM and the surrounding agent framework. The code and data are publicly available at https://dumatebench.com/.

## 2. 论文提出的方法论

**核心思想：** 从真实用户会话中重建忠实、可执行、无泄漏的任务实例，注入三类现实环境复杂性，并通过确定性检查与LLM评分相结合的方式评估异构产出物。

**关键技术细节——任务构建流水线（三阶段）：**

1. **交互历史重建（Interaction-history reconstruction）**：
   - 从匿名化、隐私筛选的生产级智能体平台会话中采样
   - 保留用户可见内容（用户消息、显示的智能体响应、文件引用、历史产物），剔除内部执行记录（工具调用、执行结果、编排消息）
   - 丢弃过于简单的会话（单轮交互、无明显工具/文件活动的会话）

2. **截断点指令制定（Cutoff-based instruction formulation）**：
   - 使用 Claude Opus 4.8 辅助选择目标用户请求，将截断边界置于目标请求首个用户轮次之前
   - 截断前的用户可见事件构成历史上下文 Hc
   - 将目标请求的所有用户轮次整合为自包含的任务指令 qc，保留原始目标、交付物、文件引用和约束
   - 排除截断后产生的智能体响应、工具输出和生成产物，防止解泄漏

3. **工作区重建（Workspace reconstruction）**：
   - 识别截断点之前用户上传的文件和历史智能体产物，检查与重建指令和历史的一致性
   - 被覆盖的文件恢复至截断前最新可恢复版本；无法恢复则丢弃任务
   - 最终任务实例表示为 T_c = (q_c, W_c, M_c)

**人工验证标准（四重筛选）：** 请求保真度、工作区完整性与一致性、无解泄漏、隐私与安全——仅当全部满足时保留任务。

**环境设计（三类现实复杂性）：**

| 环境类型 | 建模内容 |
|---------|---------|
| **Insufficient（不足）** | 基础镜像仅提供通用工具（bash、curl、git、poppler-utils等），不预装任务特定系统包与Python库；容器限制为2 CPU、8GB内存、12GB存储、1800秒执行时限 |
| **Unstable（不稳定）** | 启动阶段DNS故障、丢包延迟、目标阻断各启用8秒；执行期故障守护进程每45秒以不同概率采样三类网络故障；OCR工具层注入首次调用失败和延迟响应 |
| **Noisy（噪声）** | 保留原始会话中的自然噪声（无关/冗余/过期材料、相似命名但内容不同的文件）；低/中/高三档注入种子化合成干扰物，分别扰动约35%/65%/100%的工作区文件，上限为每任务3/6/10个文件 |

**评估协议（混合评估）：**

- **确定性检查表**：1,257个原子检查项，平均每任务6.29个；覆盖输出存在性与位置（38.35%）、必需内容（36.52%）、格式有效性（18.14%）等；任务部分通过率 P_t = (1/n_t) Σ c_t,i，仅当全部检查通过才算完成。
- **基于评分标准的LLM评判（Rubric-based LLM-as-Judge）**：454个产物特定评分文件、2,308条原子标准（平均每任务11.54条），覆盖需求完整性（34.23%）、呈现可读性（11.92%）、功能正确性（10.88%）等维度；评判模型为Gemini-3.1-Pro-Preview；未评估标准计零分，多轮评分取中位数。
- **分数聚合**：最终分数 F_t = 0.3·P_t + 0.7·J_t（30%确定性需求覆盖率 + 70%产物质量）。

## 6. 论文的主要结论与发现

1. **跨智能体框架的性能差异显著**：DuMate在每个模型组内排名第一（Final分数范围0.8046–0.8548），但领先幅度随基础模型变化（1.01–3.67个百分点）。不同框架对基础模型的敏感性差异巨大：DuMate跨模型范围仅5.02个百分点，而OpenClaw达20.66个百分点。
2. **最佳模型因智能体而异**：Opus-4.8在Claude Code和DuMate上最佳，DeepSeek-V4-Pro在Hermes、OpenCode和OpenClaw上最佳。**不存在对所有框架都最优的单一模型。**
3. **模型与框架存在强交互效应**：Opus-4.8虽然产生最高单点成绩（0.8548），但跨框架范围达27.27个百分点；DeepSeek-V4-Pro虽然平均分最高（0.8106），但跨框架范围最小（4.63个百分点）。仅看模型或仅看框架都无法完整刻画性能。
4. **噪声鲁棒性差异悬殊**：从正常到高噪声条件，Hermes损失20.08个百分点，而DuMate仅损失1.67个百分点，表明框架级别的文件筛选和信息定位能力对噪声鲁棒性至关重要。
5. **质量-效率存在明确权衡**：最高分配置（DuMate+Opus-4.8）同时也是最慢的（1,038.74秒/任务、156万tokens），最快配置（Claude Code+GPT-5.5，274.99秒）得分更低（0.7830 vs 0.8548）；OpenCode+GLM-5.2在token效率上表现最佳但与最高分差距明显。
6. **失败模式差异化**：两个智能体共有两大失败模式——执行不完整/预算耗尽（DuMate 28% vs Claude Code 32%）和错误实现/工具使用（30% vs 22%）；Claude Code更常出现需求/上下文接地失败（36% vs 14%），DuMate更常遭遇环境/依赖失败（24% vs 6%）。这揭示了不同的改进优先级：Claude Code需加强上下文过滤和需求追踪，DuMate需增强回退和恢复策略。
7. **整体结论**：在严格任务完成方面仍有显著提升空间，环境扰动下的表现由LLM能力和智能体框架共同塑造。

## 7. 优点

- **真实会话根基**：任务来自大规模生产智能体平台（服务数百万用户）的真实多轮会话，通过保真度、无泄漏、隐私安全等多重人工验证，比合成任务或模拟环境构建的基准更贴近真实用户需求。
- **组合式工作流覆盖**：79.50%的任务跨至少两个粗粒度场景，避免了现有基准按应用组织任务导致的能力隔离问题，真实反映了用户请求需要跨应用协调的本质。
- **环境复杂性系统化注入**：将不足、不稳定、噪声三类环境条件设计为可配置、可审计、可复现的标准化组件（支持随机种子、故障时间表、结构化日志），而非仅作为执行容器。网络故障仅作用于智能体流量，模型推理流量单独路由确保实验可控。
- **混合评估协议的严谨性**：确定性检查与LLM评分各司其职——前者验证客观可测约束（格式、内容、位置），后者评估语义质量（可读性、正确性、忠实度）；评分标准在评估前锁定并跨所有配置共享，避免输出自适应评分。
- **诊断深度**：结合鲁棒性曲线（4噪声级别）、效率剖面（延迟+token）、失败模式人工标注（50个样本/智能体），超越了单一的排名对比，提供了可行动的改进方向。
- **可复现性**：任务在隔离Docker容器中执行，环境条件参数化且带随机种子；代码和数据公开可获取（https://dumatebench.com/）。

## 8. 不足与局限

- **平台偏差**：任务来自单一平台（DuMate）的用户会话，可能无法代表所有用户、职业和工作流程；内容生成类任务占比过高（163/200），编码类仅89个且偏向于生成而非修改/推理，能力分布不均衡。
- **环境故障范围有限**：仅注入了网络层和OCR工具层的扰动（DNS故障、丢包、阻断、OCR失败/延迟），未覆盖API认证失败、第三方服务完全不可用、数据损坏、恶意文件、配置漂移等更广泛的真实故障类型。
- **评估可靠性未充分验证**：基于LLM的评分（Gemini-3.1-Pro-Preview）与人类判断的一致性未报告；确定性检查表中的“格式有效性”（228项，18.14%）偏向Markdown/SVG/PNG等文本友好格式，对复杂交互式产物（如动态演示文稿）的覆盖可能不足。
- **执行随机性未处理**：每种配置仅执行一次，没有多次运行取平均的报告，智能体执行的内在随机性和LLM采样可变性未纳入考量，可能影响结论的统计可靠性。
- **噪声实验的覆盖有限**：RQ2中仅评估了一个基础模型（Opus-4.8），无法揭示噪声鲁棒性中模型与框架的交互作用；合成噪声的注入数量和类型设定（文件数上限3/6/10）缺少对真实噪声密度分布的校准依据。
- **效率衡量维度不完整**：token使用量将标准输入和缓存读取合并报告，未单独区分推理缓存命中与未命中的实际成本差异；也**未报告GPU资源、并发设置或评估总成本**，降低了成本对比的精确性。
- **未来模型的时效性问题**：作为2026年的基准，其任务固定于当时的平台会话分布，未来工具接口和用户模式的变化可能带来基准漂移；基于LLM辅助的任务重建和人工验证的成本较高，限制了大规模扩展。
