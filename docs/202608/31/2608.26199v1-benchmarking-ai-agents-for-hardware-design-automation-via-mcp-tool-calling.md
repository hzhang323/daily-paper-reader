## 摘要
我们研究在行业现实的工具调用环境中，由本地部署的大语言模型驱动的AI代理能否可靠地自动化专家定义的硬件设计工作流。在这些环境中，工程师通过专门工具执行重复性、依赖有序的操作，如创建组件、添加端口和连接线路。组件规范与命名约定的保密性限制往往排除使用托管专有API，这促使采用本地部署模型。为了研究这一场景，我们构建了一个模型上下文协议（MCP）服务器，重现嵌入式系统开发中使用的专有硬件设计工具的状态和依赖逻辑，并构建了一个涵盖单操作编辑、多步依赖链、无效请求、拼写错误提示以及多服务器工具上下文的基准测试集。我们评估了七种开源模型，比较了系统提示、工具描述详细度、上下文范围以及单代理与多代理架构等流水线选择。结果表明，强大的模型在基准测试工作流上可以实现接近完整的预期调用覆盖率，但可靠性在很大程度上取决于任务结构和代理配置。全面的工具描述持续减少失败，少样本提示可能导致某些模型严重不作为，累积上下文会损害受限模型，多代理分解帮助较弱的工作者或长时间会话，但代价是额外调用。这些发现为在有状态硬件设计环境中部署本地LLM代理提供了实用指导。

## Abstract
We ask whether AI agents powered by locally deployed large language models can reliably automate expert-defined hardware design workflows in an industry-realistic tool-calling setting. In these environments, engineers issue repetitive, dependency-ordered operations---such as creating components, adding ports, and wiring connections---through specialised tools. Confidentiality constraints on component specifications and naming conventions often preclude hosted proprietary APIs, motivating the use of locally deployed models. To study this setting, we build a Model Context Protocol (MCP) server that reproduces the state and dependency logic of a proprietary hardware design tool used in embedded system development and construct a benchmark covering single-operation edits, multi-step dependency chains, invalid requests, misspelled prompts, and multi-server tool contexts. We evaluate seven open-source models comparing pipeline choices including system prompts, tool-description detail, context scope, and single-agent versus multi-agent architectures. Results show that strong models can achieve near-complete expected-call coverage on the benchmarked workflows, but reliability depends strongly on both task structure and agent configuration. Comprehensive tool descriptions consistently reduce failures, few-shot prompting can cause severe inaction for some models, cumulative context harms constrained models, and multi-agent decomposition helps weak workers or long sessions at the cost of additional calls. These findings provide practical guidance for deploying local LLM agents in stateful hardware design environments.

## 2. 方法论

### 2.1 核心思想
- 构建一个 **MCP 服务器**，以 14 个可调用工具（表 1）复现专有硬件设计工具的状态、数据模型和依赖约束（如端口必须先于连接存在、子组件必须先于端口引用存在）。
- 将自然语言请求翻译为**有序的 API 调用序列**，在**持久化应用状态**上操作。
- 采用**调用级（call-level）评估**而非文本输出评估，因为任务级成功可能掩盖遗漏或多余的调用。

### 2.2 关键技术细节

**MCP 服务器工具集（14 个工具，分三组）：**
- **Adder 组**：创建组件、添加信号端口、添加事务端口、添加用户参数、添加生成器参数、添加子组件、添加子组件连接
- **Getter 组**：获取组件详情、获取元素、列出组件
- **Other 组**：删除元素、删除组件、保存组件、加载组件

**代理架构（两种对比）：**
- **ReAct**：单代理循环，每轮发一次工具调用。
- **Plan-and-Act**：多代理结构——规划者分解请求 → 验证者检查计划（允许一次重新规划）→ 独立 ReAct worker 执行各步骤 → 综合最终答案。

**配置维度（消融变量）：**
- **系统提示词** 4 种：无（仅工具模式）、基础、MD（Markdown 结构化）、few-shot（基础 + 示例）。
- **工具描述格式** 2 种：全面（目的、参数语义、约束、失败条件）vs 极简（单句话，省约 2000 tokens）。
- **历史范围** 2 种：run scope（跨任务累积全部历史）vs task scope（每任务全新上下文）。
- **温度**：默认采样温度（1.0，Llama 3.1 8B 为 0.8），另测 0 和 0.5 做稳定性检验。

**评估指标（4 个，需联合解读）：**
- **Expected Call Coverage (ECC ↑)**：正确执行的预期调用数 / 预期调用总数，衡量任务完成度。匹配需工具名和参数值均正确，顺序不敏感（依赖违规由服务器拒绝）。
- **Extraneous Valid Call Ratio (EVCR ↓)**：成功但非请求的调用 / 成功调用总数，衡量过度生成。
- **Tool Failure Rate (TFR ↓)**：被服务器拒绝的调用 / 总调用数。
- **No-Call Accuracy (NCA ↑)**：空预期任务中未做任何调用的比例，衡量正确弃权。

**评估协议**：任务按顺序呈现，每任务后重放预期调用序列恢复服务器规范状态，防止单个错误级联，同时保留 History/Cross 套件的状态依赖。

## 6. 主要结论与发现

1. **强模型可达近完美覆盖**：最优配置下 Gemma 4 31B 平均 ECC 达 0.990，Gemma 4 26B 为 0.958，证明本地开源模型在硬件设计工具调用场景中可行。

2. **模型选择决定性能上限，配置决定是否达到上限**：
   - 任务越复杂（需状态恢复与依赖管理），模型间差距越大（如 Cross 套件上 Gemma 4 E4B 比 Gemma 4 31B 低 47 个百分点）。
   - 同一模型在好/差配置下 ECC 差异巨大（Gemma 4 E4B 从 0.811 跌至 0.168），且全局最优配置并非各任务套件最优配置。

3. **综合工具描述是收益最一致的配置选择**：切换为极简描述后，所有模型的 TFR 均上升（多数翻倍）；83% 的模型-任务套件组合最优配置采用综合描述。

4. **少样本提示存在"灾难性不作为"风险**：Gemma 4 31B 和 Gemma 4 E4B 的 ECC 分别从 0.956→0.571、0.731→0.179，EVCR 和 TFR 同步下降，说明模型停止行动而非行动出错。

5. **累积上下文对受限模型有害**：Llama 3.1 8B 在独立任务上累积历史使其 ECC 从 0.667 跌至 0.192（降 71%），表现为沉默而非更多错误调用。

6. **多代理分解（Plan-and-Act）的适用条件**：
   - 弱 worker（Llama 3.1 8B）受益显著：平均 ECC 0.554→0.718，History 上 0.113→0.650。
   - 强 worker（Gemma 4 26B）单代理反而更好。
   - 长会话（Hard-Noise 60 任务累积历史）下恢复覆盖率 0.858→0.950，但代价是 EVCR 升高。

7. **多服务器上下文的成本**：并置 GDB/Git 服务器不损害 ECC，但提高所有测试模型的 EVCR（更多无关路由错误）。

8. **稳定性**：温度 0/0.5/默认下模型排名和绝对性能稳定（Gemma 4 26B ECC 范围 0.881–0.896）；重复运行方差低，最大离群值恰为少样本崩溃配置，确认该效应真实。

## 7. 优点

- **场景真实性强**：MCP 服务器复现专有工具的状态与依赖逻辑，任务由专业用户定义并验证，非人工合成。
- **评估指标设计精细**：ECC/EVCR/TFR/NCA 四指标联合解读，既衡量覆盖率也捕捉过度生成和工具调用失败，匹配顺序不敏感但依赖违例由服务器实体制裁。
- **配置维度覆盖全面**：同时考察提示词、工具描述、上下文管理和架构选择，并揭示这些因素的**交互效应**（如少样本与特定模型不匹配）。
- **实验严谨性**：包含温度扫描、多轮重复、最佳/最差配置对比、干净-含噪配对基线，并排除采样噪声干扰主效应。
- **发现具有可操作性**：五个部署实践（在目标模型上测试提示词、用综合工具描述、按任务代表性子集做基准、管理受限模型的上下文、为弱 worker 或长会话保留多代理）可直接指导工业落地。

## 8. 不足与局限

- **上下文管理的探索范围有限**：仅测试了"全保留 vs 全重置"的二元选择，未探索记忆窗口、摘要或选择性遗忘等中间机制；更长的会话序列（现在是几十个任务）可能对更多模型产生上下文退化效应。
- **EVCR 缺乏严重性加权**：额外用户参数与错误子组件连接对设计正确性的影响完全不同，但当前指标等权对待。
- **未测量响应延迟**：本地推理时间随模型规模显著增长，延迟敏感部署可能偏好更小模型，这一权衡未被捕获。
- **生产保真度有限**：MCP 服务器是对专有工具数据模型和依赖规则的**忠实复刻**，并未调用其生产 API，代理行为与真实生产的差距不可估量。
- **不可复现性**：服务器实现和基准任务均**不能发布**（编码了专有组件规格和工作流细节），仅附录提供了代表性示例，第三方难以完全复现。
- **模型集局限**：评估的均为开源模型中较新的一批，温度和配置搜索范围有限（未测 top-p 等采样参数、更极端的量化级别），结论的一般化需谨慎。
